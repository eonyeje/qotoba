Qotoba Applications

Four applications are rewritten in Qotoba: Dope, the media library that already drives the framework; KraveSoccer, a football app; Entrepreneur, a business simulation game; and KraveFlow, a production ordering platform for distributors and their resellers. Each is a parity exercise against something that exists, and each teaches the platform something the others cannot.

Sequence

The order and why

Dope goes first for three reasons that no other app has: it is the framework's existing test bench with 15 design documents and 13 suites to compare against; it has a parallel WinUI rebuild with 1,140 checks that define its behaviour independently of the framework; and its screens already cover the hardest cases, from a 1,356-movie virtual library to seven HTTP providers. If Qotoba can write Dope, it can write an application. KraveSoccer follows because it is small and forces the mobile head. Entrepreneur follows because its simulation and map need the process family and custom drawing, which Dope never touches. KraveFlow is last to onboard a principal because it is production, but its backend modules start as soon as the services family exists, because they are the cleanest test of server emission.

A decision for the owner (Q-09)

If commercial pressure puts KraveFlow ahead of Entrepreneur, the plan holds: KraveFlow's backend lane already starts in phase D, and the console can take Entrepreneur's slot. Nothing in Entrepreneur is on KraveFlow's path.

What an app looks like in Qotoba

Every app is the same set of intent families, in files a developer can read top to bottom. The framework owns the how; the app declares the what. The target is the one Quanta already sets: ten lines or fewer of real code per screen, process, query or model.

Application 1 · phase D

Dope

What it is
A media library for movies, TV, people and collections, drawing on TMDb, TVDB, OMDb, YouTube, Radarr, Sonarr and Streaming Availability. 1,356 movies and 237 collections in the reference library.
Reference versions
The Quanta version, 447 files, 13 suites, 15 design documents; and the WinUI rebuild, 278 files, 919 console checks and 221 UI checks, written in Quanta's shape with no Quanta library.
Target
Desktop, C# on the Qotoba framework, through the MAUI host until Q-13 moves it.
Bars to meet
Library opens within 500 ms; no 5 to 7 second freeze after the library answers; the eleven remedies' gains held.

Intent families Dope uses, with the ones it introduces to the programme marked:

appschemasource ×7viewwidgetinteractionservicestest

Shape of the rewrite

  1. Schema and sources first. The seven APIs become source declarations carrying what the [HttpApi] attributes carry today: rate interval, bearer credential, JSON error shapes, cache, coalesce, paging. The 33 hand-written TMDb response classes become generated records. Proof: Dope's data suites pass against the emitted client.
  2. Views. The library, dashboard and collection queries become view declarations with clauses. Proof: the same rows in the same order as the Quanta queries, timed.
  3. Screens by the §16 walk. Each page is designed as view trees, a model outline, queries and delivery before it is written as a widget. Movies page, movie page, person cards, the card rail, the collections tab, settings. Proof: screen gate against the Quanta version's screenshots; the ten-lines measure per screen.
  4. Verbs as interactions. The card verbs with confirmation and undo from the basket, built lazily as the lazy-verb finding requires. Proof: the 130 MB per visit saving holds.
  5. The head. One app declaration. Proof: the app starts from emitted code with no hand-written C# in the app folder.

What stays hand-written during the rewrite: nothing in the app. A framework gap found on the way is a register item in framework terms, and the screen waits for it rather than working around it. That rule produced most of the redesign's real cases, and it is the only way the ten-lines target stays honest.

Application 2 · phase E

KraveSoccer

What it is
A football app. The Quanta version is a light second app shape of 14 files; the Dialect-era version, 253 files in Core and UI projects, holds the fuller feature set; a 2023 Flutter shell exists with no code.
Reference version
The Dialect version for features; the Quanta version for the current framework shape.
Target
Mobile first: Android and iOS from one Qotoba source through the C# target and the mobile head. Dart and Flutter are the natural second target once WS2-8 proves the emitter shape, which makes KraveSoccer the test case for the second platform.
app (mobile)schemasourceviewwidgetinteractionenvironment (device)device servicestest

KraveSoccer opens the phone: the environment source filled with device model and battery, push notifications, and whichever of the 40 device services the feature list needs first. It is deliberately small so that the mobile head and the first device contracts are proved on an app that fits in a week of nights. Its feature list is recovered from the Dialect code before design starts, as a parity page, so nothing is dropped.

Application 3 · phase E

Entrepreneur

What it is
A business simulation game with a map. Three Quanta projects: App, AppUi and Simulation, 36 files; a five-file remnant in the Jargon repository.
Reference version
The Quanta simulation and its suite; the Entrepreneur design system page for the visual target.
Target
Desktop, C# on the framework; custom render widgets for the map through extern drawing onto the Skia surface.
appschemaprocessstate machinewidgetextern (drawing)interactiontest

Entrepreneur is where the process family and the state machines earn their place: a simulated year is a process with timed events, a market is a state machine with explicit ignore policies, and the map is a widget whose body draws through extern calls to the graphics layer. It also tests a kind of app the ten-lines rule finds hardest, where the real code is the simulation itself. Proof is a full simulated year producing the same outcomes as the Quanta suite, and the map rendering through the headless host within its frame budget.

Application 4 · backend lane from phase D, console in phase E

KraveFlow

What it is
An agent-agnostic integration layer that lets distributors and manufacturers in Nigeria sell to their resellers through AI agents on WhatsApp, SMS and email, while their ERP stays the system of record and a partner bank holds the money in escrow. Fifteen modules plus a platform foundation; architecture draft v0.1 of 9 October 2026, owned by KraveX Limited.
Reference
The architecture draft: Level 1 and Level 2 designs, key flows, two state machines, the data model, deployment as a modular monolith on .NET with PostgreSQL and row-level security, and its non-functional targets.
Agent platform
Lua, or any agent that can call REST or MCP tools. The agent owns the conversation; KraveFlow owns every fact and action, and never does the maths in the agent.
Target
Server: C# through Qotoba.Server (minimal API, outbox, OAuth2, signed links, audit). Admin console: TypeScript through the widget intent. Driver link: a web page from the same widgets.
app (server)schemaviewservices ×15 modulesapiEndpointtool (MCP + OpenAPI)processstate machinewidget → TStest

Phase 1 as the architecture defines it

The ordering core: Agent Gateway with REST and MCP from one definition, Identity and invites, Catalogue, Orders, Integration Hub with one ERP adapter and the shared back office, Messaging, direct payment through virtual accounts, Tenant Admin basics, Billing metering with Zoho sync. Escrow, the driver link and OTP, Customer Service, Promotions with campaigns and tenant reporting are phase 2; remaining adapters, dedicated cells and platform analytics are phase 3.

Why KraveFlow is the best server case

  • The gateway is a tool intent made real. KraveFlow's own design says the tool API, as OpenAPI and MCP from the same definitions, is the product. One Qotoba declaration emitting a handler, a JSON schema and an OpenAPI operation is exactly that.
  • Its flows are processes. Order to cash, delivery and escrow release, service escalation, onboarding and monthly billing are drawn as sequence diagrams in the draft; they become process declarations, and the Order and Escrow state machines become state machines with explicit policies.
  • Its foundation is the framework's server group. Transactional outbox, webhook ingress with signature checks, OAuth2 and OIDC, tenant isolation, append-only audit: these are WS5-8, built once as Qotoba.Server and reused by every server app after.
  • Its targets are measurable. p95 read under 800 ms, quote under 2.5 s, zero lost orders, zero cross-tenant reads, 99.9% gateway availability. The parity page for KraveFlow is its non-functional table, run in a staging cell.
Production rules
  • No principal is onboarded until phase 1 passes its non-functional targets in a staging cell and the emitted C# has been reviewed as C# by the owner through the generated-code review page.
  • The bank holds the money. KraveFlow's ledger is instructions and bank confirmations, never balances, in Qotoba as in the draft.
  • KraveFlow's six open questions (bank capabilities, agent metering, dispute window, first ERP adapter, data residency, rate card) are decision cards of their own, asked when the backend lane opens.

What each app teaches the platform

Dope

Whether the schema, source, view and widget families can carry a real data application, and whether the framework's refresh-in-place and virtual loading survive being declared instead of written.

KraveSoccer

Whether the mobile head and the first device services work from one source, and whether the emitter shape holds for a second platform when Dart arrives.

Entrepreneur

Whether processes, state machines and extern drawing read as one language with the UI, and whether a simulation can be real code without breaking the ten-lines rule for its screens.

KraveFlow

Whether services, endpoints, tools and processes emit a production server that meets numbers, and whether one declaration can serve an agent, a console and an audit at once.

Together they cover every kind of app the founding requirements name except console tools, OS services and data science, which the app family leaves room for and which phase F can add without a new application.
