Quanta Baseline

Qotoba is the public, production version of the Quanta components. This page records what Quanta has today, from the two overview documents and the repository on master, so that the plan builds on measured ground and nothing is rebuilt that already exists.

Sources: Quanta — The Complete Overview · Quanta — The Vision · Quanta Workbench tooling plan · master at de7865f9

Why a baseline comes first

Quanta is about 387,000 lines of C# in 2,130 files, built by one developer directing many Claude sessions over a year. It has four parts in very different states: a large, proved Framework; a Language whose new front end is finished to the type model and whose back half exists only as design; a Workbench that is working and in daily use; and an early ADE. The plan's first rule is that Qotoba inherits all of it rather than starting over. The second rule is that each part moves to the public name only when its public shape is agreed, which is why this page separates built from designed from vision at every step.

Status key used throughout the plan

Built in code on master with tests · In progress partly built · Designed written down and agreed · Vision intended with no agreed design · Gap a known fault or missing piece.

Two more facts shape the plan. The Workbench survey measured 6.7 hours a day of Claude work across 56 days, with 302 incidents in 20 kinds, and it priced the eight worst patterns at about 50 hours of lost owner time. Estimates in person-days came out four to six times too long; the Workbench now estimates in Claude-minutes. The plan uses session-hours for the same reason.

The Framework

A UI and application framework written from the ground up in C#: its own values, events, collections, meta-elements, layout, rendering on Skia, data source and task engine. MAUI only hosts it. It pursues one target: a screen, process, query or model written in ten lines or fewer of code that is about the app, with everything else coming from a piece that already exists.

The redesign matters to Qotoba because the language's intents distil onto the framework: a `widget` becomes a UI element, a `schema` becomes data models, a `process` becomes a BPMN process. The redesign's lab has already settled the shapes the distiller will target: `partial` alone marks an observable member, processors on a value, one task type with runner chains, and simple composable collections. Lab benchmarks read 6 ns for a read through a handle and 25 ns for a write with one follower, with no allocation.

The Language

Quanta's own language exists so an application can be written as intent. Intent code distils into primitive code that runs on a runtime in debug and transpiles to C# for release. Two front ends exist today: the old one in Quanta.Language, which is the only code that runs a program and which ADE and the query layer use, and the new Quanta.Parser, 184 files and 21.8k lines, self-contained and referencing only Core.

What the design has settled: 52 reserved keywords and 16 contextual words; a syntax that reads like Swift or Kotlin; one naming rule where typedef, intent and syntax all bind with =; intents as plain classes with one build(name) method; four domain syntaxes (UI, process, data, schema) sharing modifier chains, match, |> and trailing lambdas; reactivity in the type system through bind and observe; extern for platform contracts; four injection sources (environment, services, config, vault); and a context cascade.

What the design has not settled, and what Qotoba must settle first: the error-handling model, the async and concurrency model, nullability, and generics with constraints. The Vision document calls these "the four foundations" and notes that the standard library zoning and the transpiler capability manifests all wait on them. The sources also disagree on the file extension (.qnt against .qn and .q), the keywords (func/let against fn/val), and whether config is an intent or a built-in source.

The Workbench

An ASP.NET Core minimal API over SQLite on localhost:5190, with a single-page front end, reached by sessions as an MCP server with 38 tools and through hooks on every session event. It holds rulings, cards, pages, tasks, units, gates, stages and packets; sessions act on git only after the owner presses a button. Slices 1 and 2 are built and merged, with 16 suites and about 547 checks. Slice 3 (design review on a Roslyn code index, an API class view, widget mimics) and slice 4 (prototypes drawn from widget code) are designed.

Baseline

ADE

A visual development environment of 130 files in four projects, written against the framework and running on the language's first front end. It has a project tree, typed designers for classes, interfaces, extensions and enums, a widget design surface with device skins, an inspector, palettes of 18 widgets and 14 modifiers, and Build, Generate Quanta, Generate C# and Run commands.

What ADE cannot do yet
  • Opens one built-in sample project and nothing else; no open or save.
  • The code editor is a plain native text box: no colouring, findings, completion or line numbers.
  • Generated code goes only to the log; no debugging and no test running.
  • Runs on the first front end; moving it to the new parser is a registered task of about ten days with no design document.
  • No charter, brief, architecture or design document on any branch; no owner ruling names ADE.

The vision for ADE is one tool, written in Quanta, with six reactive editors over one source (text, widget canvas, inspector, process, schema, query), session and personal overlays, hot apply, and six debug views keyed by provenance. None of that is built. This is why the plan reorders ADE: the editors arrive first inside Rider and VS Code, where a language server and a web UI give most of the value at a fraction of the cost, and the standalone tool follows once the language can write it.

What carries over, what retires

Carries over as is

  • Quanta.Parser: lexer, parser, records, printer, identity, lookups, type model, generators, 2,545 checks
  • The Framework groups and their suites, catalogues and generators
  • The Workbench: schema, 38 tools, hooks, templates, gates, night shift
  • CLAUDE.md's working method: BREEO, §16 screen design, the registers, ten lines of real code
  • The language's agreed designs: naming rule, intents, domain syntax, reactivity, injection, extern
  • KraveFlow's architecture draft

Retires or is replaced

  • The old front end (Quanta.Language, 109 files) once ADE and the query layer move; seven known bugs close with it
  • The Reflection.Emit type builder and the old interpreter, replaced by the C# emitter and later the new interpreter
  • ADE's native text box, replaced by the language server in the IDE
  • The catalogue scan, replaced by a code index
  • Quanta namespaces, renamed to Qotoba on a planned date

Open points the plan inherits

The two overview documents end with lists of undecided points. The plan does not decide them; it schedules them. Each appears again on the decisions list with the stage that needs it.

  • The four language foundations: error handling, async and concurrency, nullability, generics with constraints.
  • The file extension and the keyword set, where sources disagree.
  • Whether the Workbench moves into ADE, or ADE's panels move into the Workbench, or both share one web UI.
  • ADE has no charter; the acronym is never expanded.
  • The night shift has never run on its own; measured minutes read zero on every task; the commit flow assumes a branch is one task.
  • 39 register IDs clash across four branches; 141 unregistered items wait.
  • How Dope's WinUI rebuild relates to the framework, and how its findings reach the registers.
  • When to move the platform host from MAUI to Avalonia, and the 40 device-service contracts.
  • KraveFlow's six open questions: bank capabilities, agent usage metering, dispute window, first ERP adapter, data residency, rate card.
