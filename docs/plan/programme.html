Qotoba Programme Plan

The plan and working strategy for taking the Quanta components to Qotoba, the public production platform: a language, a framework, IDE tooling and a Workbench, built so that most of the work is Qotoba building itself, and then used to write Dope, KraveSoccer, Entrepreneur and KraveFlow.

Owner: eonyejeBuilders: Claude sessions through the WorkbenchHorizon: six phases, about ten months at planned capacity

Mission and scope

The goal in one sentence: use the Qotoba language and ADE tools to develop modern multi-purpose apps on top of the Qotoba framework, manage the work and the interaction with AI agents in the Workbench, and have the code translated to the language of choice and compiled into the final running application.

Four things follow from that sentence and set the plan's priorities.

  • The language must emit real code early. The quickest route to "it runs" is not the interpreter but a C# emitter over the existing .NET toolchain. The interpreter and the debug runtime come later, once there is something worth hot-patching.
  • The tools arrive inside Rider and VS Code. One language server in C# and one web UI in TypeScript serve both IDEs. This is the first place Qotoba's own output ships: the add-ins' UI and service layers are the first code generated from Qotoba source, and once the emitter can carry it, the whole language server is rewritten in Qotoba and its C# generated.
  • Qotoba builds Qotoba, all of it. The target is 100% of the toolchain generated from Qotoba source, compiler included, with hand-written C# serving only as bootstrap. Rewriting the language server in Qotoba is what gives the language its constructs for language development: syntax rules, findings, editor features and emitters as intents.
  • Apps follow in a set order. Dope first, because it already drives the framework and has the most checks to compare against. Then KraveSoccer for the mobile shape, Entrepreneur for custom rendering, and KraveFlow as the production backend and the agent-platform case.
  • The Workbench and the agent surface are products, not side tools. Overload is the known failure mode: 302 incidents, 50 hours of priced waste. The plan funds the gates, pages, MCP tools and Skills that keep the owner reviewing cards rather than code.
Out of scope for this plan

The five non-C# targets (Dart, Kotlin, Swift, TypeScript beyond the add-ins, Python) beyond proving the emitter shape; the standalone Quanta-written ADE as a product; the public launch, pricing and community. Each gets its own page when its phase opens.

The strategy: Qotoba builds Qotoba

"Most of the work would be Qotoba building itself" is the governing idea, and it has to be made concrete or it becomes a slogan. Self-hosting is a ladder with measurable rungs. At each rung a named piece of the toolchain stops being hand-written and starts being generated from Qotoba source, and the share of generated code is measured and reported by the Workbench as a gate. The end state is 100%: Qotoba builds Qotoba. Hand-written C# exists only to bootstrap. Once the C# emitter can carry code of the language server's complexity, the language server is rewritten in Qotoba and its C# is generated; the compiler itself follows as the last rung. Rewriting the server in Qotoba is also what gives the language its constructs for language development: intents for syntax rules, findings, editor features and emitters, so that building a language tool becomes an ordinary Qotoba program.

0
Hand-written kernel

Binder, validator, distiller, C# emitter, CLI and the language server's protocol layer are written in C# by sessions, on the existing parser. The web UI shell and the VS Code shell are written in TypeScript. Nothing is generated yet.

generated share0%

First light

A sample app in Qotoba emits C#, builds with dotnet and runs on the Qotoba framework. The language server reports its diagnostics in VS Code and Rider. This rung proves the pipeline before anything is self-hosted.

generated share0%
2
The add-ins' UI is Qotoba

With the widget intent and the TypeScript emitter, the web UI panels (project tree, inspector, generated-code view, Workbench panel) are rewritten as Qotoba widgets and emitted as React components. The hand-written TypeScript shrinks to the host shell.

generated share~30%
3
The language server's services are Qotoba

Hover, completion, go-to-generated and the catalogue queries are declared as Qotoba services over the compiler's API and emitted as C#. The protocol layer is still hand-written at this rung, and the emitter is measured against the complexity corpus: async, generics with constraints, interfaces, pattern matching, records and JSON-RPC protocol types.

generated share~45%
4
The whole language server is Qotoba

When the complexity corpus is green, the language server is rewritten in Qotoba, protocol layer included, and all of its C# is generated. The rewrite is done with the new language-development intents: syntax for lexer rules, finding for diagnostics, feature for completion, hover, code actions and navigation, and emitter for output templates. From here, adding an editor feature to Qotoba is writing Qotoba.

generated share~70%
5
The Workbench's pages and the MCP tools are Qotoba

Workbench pages are widget intents; MCP tools are tool intents emitted as both C# handlers and tool schemas. The same definition serves the add-in, the Workbench and the agent.

generated share~80%
6
Apps are Qotoba

Dope, KraveSoccer, Entrepreneur and KraveFlow are written entirely in Qotoba. The framework is the runtime they distil onto and stays C#.

generated shareapps 100%
7
The compiler is Qotoba

Binder, validator, distiller and emitters rewritten in Qotoba with the language-development intents, their C# generated by the previous compiler, which then becomes the bootstrap. The parser follows the same way. At this rung every line of the toolchain is generated from .qo source.

generated share100%

The percentages are targets for the toolchain's own code (compiler, language server, add-ins, Workbench, agents), measured as lines of C# and TypeScript emitted from .qo source against lines written by hand. The framework is the runtime, not the toolchain, and is counted separately; whether it too is rewritten in Qotoba is a phase F decision (Q-14). The Workbench's self-host gate, defined on the tooling page, reports the number on every packet so the trend is visible and a regression is a warning.

Why this order

UI first because a widget intent emitting React is the simplest end-to-end case: no async model, no persistence, and a failure shows on screen. Services second because they need the injection sources and the async model, which are two of the four foundations. The whole server third because it is the first program complex enough to prove the C# emitter on real systems code, and because rewriting it is what designs the language-development intents against a real tool. Tools and Workbench pages next because they need both. Apps after, because each has an existing version to compare against. The compiler last, because by then the language has every construct the compiler needs and a previous compiler to bootstrap from.

The complexity corpus

A fixed set of Qotoba programs that represent the language server's hardest shapes: an async JSON-RPC loop, generic request handlers with constraints, interfaces with default members, exhaustive pattern matching over protocol unions, records with provenance, and a cancellation-aware pipeline. The C# emitter is "complex enough" when every corpus program emits, builds with warnings as errors, and passes its checks. That is the gate that opens rung 4, and it is a named task (WS2-9) so the moment is measured, not felt.

The first deliverable

Rider and VS Code first

The brief says C# for the language server and TypeScript for the UI. The plan keeps exactly that, with one unavoidable addition: Rider plugins are IntelliJ plugins, so a thin Kotlin shell registers the language server and hosts the web UI in a tool window. The shell contains no logic. Both IDEs run the same server process and load the same UI bundle, so every feature is built once.

What the first add-in release must do, in order of value: show diagnostics as you type, with the parser's recovery so the tree is always complete; complete keywords, members and intent bodies; hover to show the type and a preview of the generated code; jump from a .qo line to the generated C# and back through provenance; format through the printer; and open the Workbench inbox in a panel so the owner never leaves the IDE to press a card. Debugging is through the emitted C# with #line directives mapping back to the .qo source, which gives breakpoints in Rider and VS Code without a debug runtime.

The critical path

Everything that matters to "Qotoba builds Qotoba" sits on one chain. A slip anywhere on it moves every later date; a slip off it does not.

Off the path, and runnable in parallel: the framework's core redesign, the Workbench's language gates, the MCP server, the Skills pack, KraveFlow's backend modules, the interpreter.

Two items deserve a note. The core redesign is off the path only because the emitter can target the framework as it is today and move to the redesigned constructs when they land; the distiller's output shape must be designed so that switch is a mapping change, not a rewrite. The interpreter is off the path because C# emission plus dotnet gives a running program; the interpreter earns its place when hot apply and overlays open in phase F.

Working strategy

How we work

The Workbench's rules W1 to W14 stand. The owner's job is to decide and to judge; sessions design, build, test and commit; machines check before the owner reads. The rhythm below is the plan's expectation of a working week once phase A is in motion.

Morning, 30 minuteson the phone or in the IDE panelRead the overnight summary. Press Approve or Change on packets. Answer question cards in one pass. Nothing read raw.
Day, one design lanechat, with pages for anything longOne design conversation at a time: BREEO walk, §16 screen walk, or a foundation decision. The session records rulings the same day.
Evening, 15 minutesthe night cardApprove the night's batch: which tasks, how many sessions. Three sessions build against approved designs from 22:00.
Night, machines22:00 to 07:00Sessions build, run suites, meet the gates, draw packets. A failure gets two self-repairs before it becomes an alert. Questions become cards for the morning.
Weekly, one hourthe boardRead the self-host gate trend, the forecast, and the late cards. Move the forecast only here.
Phase gateone page, one cardThe phase's exit criteria as a packet. Approving it opens the next phase's lanes and recalibrates estimates.

Rules the plan adds to W1 to W14

  • Qotoba code is written through the Skills. A session that writes .qo without the language Skill loaded is a finding in Health, because that is how dialects drift.
  • Generated output is never edited by hand. The generated/ folder is read-only by hook; a change belongs in the source or in the emitter, and the emitter's golden baseline shows which.
  • Every emitter change ships with its diff. The packet for an emitter change carries the baseline diff for every corpus file, folded, so the owner sees what changed in the output without reading the emitter.
  • An app never names a framework gap as app code. Carried over from Quanta: the gap is a register item, in framework terms, and the app's packet lists it.
  • One decision card per foundation. The four language foundations are never settled inside another task's packet.
