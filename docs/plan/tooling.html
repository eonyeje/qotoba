Workbench and Agent Tooling

Building five products and four apps with agents produces more output than one person can read. This page lists every tool the plan needs so the owner's work stays simple: what exists, what is adapted, what is new, and the measurement that says whether it is working.

The overload problem, measured

The Workbench exists because of a survey of 55 sessions over 56 days. Its summary: "Your time went into reading and correcting rather than deciding. Claude was not checked by anything except you. Knowledge lived in chats and drifted across branches. And there was no unit of review bigger than a message and smaller than a month." The Qotoba programme adds a new kind of output on top: generated code in two languages, which nobody wrote and which must still be judged.

302incidents in 20 kinds across the surveyed sessions
~50 hof owner time priced to eight patterns: unattended runs, question drip, rubber stamps, pasted hand-offs, rules in chat, lost context, buried questions, colliding branches
244 / 633owner messages in one session that answered a turn-ending question
< 1 minthe Workbench's target for every decision, on a phone

The governing requirement, in the owner's words: "i do not mind even up to 8-10 hrs of review - the main issue is how easy it is to review." Volume is acceptable; friction is not. Every tool below is justified by one of the twenty incident kinds it removes, or by the new generated-code review load it absorbs.

In the IDE

The IDE panel

The owner's working rule is three places and no fourth: Claude Code, the IDE and the Workbench. The add-ins let the Workbench be a panel in the IDE, from the same web UI bundle the ADE panels use, so a card is pressed where the code is read.

Scope for the first release: the inbox with its buttons, the project page with its three presses, and the current task's packet. The board, timeline and registers stay on the web app until the panel proves itself. The panel is a widget intent from rung 2 onward, which makes it the second self-hosted piece after the generated-code view.

Hooks

Hooks run on session events and tool calls; they are the checks a session meets before the owner sees anything.

  • On every .qo write: run the printer and the validator; reject the write if the file does not round-trip or has a failing finding, and return the finding to the session.
  • Before a tool call: block any edit under generated/; block a push to master without a Push press; block a full solution build nobody asked for.
  • On session start: load the brief, and record which Skills are loaded; writing .qo later without qotoba-lang is a Health finding.
  • After each tool call: stream progress to the live strip; attach provenance to any diff of emitted output so the review page can align it.
  • On stop: post the session state; refuse to stop while a reply is unread.

A tool is working when the owner's reading stays inside a budget. The plan sets one and the Workbench reports it weekly on the board, from the session ledger and the card timestamps.
