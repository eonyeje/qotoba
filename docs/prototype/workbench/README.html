Workbench prototype guide

A clickable HTML prototype of the Qotoba Workbench: sixteen screens and ten page templates, three layouts, light and dark, filled with one consistent snapshot of the programme at 05:12 on Friday 6 November 2026. Revised the same day: every screen now leads with the one thing to decide, and everything else waits one tap away. Revised again: features, bugs and performance problems are now issues kept apart from tasks, each with its own report page. Use this page to review the prototype against the brief.

HTML, CSS and JavaScript onlyno build, no networkopens from the file system

Open it

Open index.html straight from the file system or any static server. The header holds the layout switcher (Phone 390 px, Rider 460 px, Desktop 1200 px and up), which constrains the shell to that width so all three can be reviewed in one browser window. Press ? or the grid button for the Screens drawer: every screen, sample card, item, template, overlay and empty state by name, plus layout and theme switches. Theme follows your system; the drawer and Settings can force light or dark.

Design approach

The Workbench exists to cut what reaches you, so each screen shows the least that lets you decide and lets you go deeper one section at a time.

  • One decision first. A card opens on its kind, one sentence, the choices and the buttons. Nothing else is open.
  • Drill rows for the rest. Every other section is a single line: a label, a one-line summary, a chevron. Open the ones you care about. A small amber dot marks a row that deserves a look, for example “2 assumptions to review”.
  • “Worth a glance” on packets. Under “All 5 checks passed” sits the short list of exceptions. Each one opens its own section.
  • Tabs for long pages. The task page has seven tabs: Overview, About, Plan, Changes, Issues, Decisions, Activity. An issue report has five: Report, Plan, Changes, Decisions, Activity. Old tab links (questions, runs and so on) still work and open the matching section.
  • Your own words on every card. Question, Approve, Plan, Stuck and Info cards each have a reply box beside the default buttons. Type a message and press Send or Enter; it goes to the session that raised the card. Approve's “Ask for changes” opens the same box, with no picker.
  • Quiet chips. A chip shows its icon and title only. IDs, dates and back-links are inside the popover under “Where it came from”. Breadcrumbs are plain links.
  • Short lists. An inbox card has a kind, a headline and one line of context, with no buttons. “For you to know” is folded into one line. In the tree each row is a title and one state word, and filters sit behind one Filter button.
  • Space. Wider margins, a reading column of about 780 px on desktop, a one-row header, and the project filter as a single menu.

Issues and reports

Tasks and issues are two separate lists. A task is part of a project's work breakdown, the tree under Work. An issue is a feature, bug or performance problem (FTR, BUG, PER) that comes up while a task is being built. It is attached to that task, or to a project when no task fits, but it is its own record with its own report, state, time and dependencies.

  • Where issues show. The Issues screen lists every issue grouped by the task it hangs off, with filters for kind and “needs me”. Work has a Tasks | Issues switch. Each task has an Issues tab, and a tree row carries a small issue count. Desktop and Rider also show Issues in the navigation; on phone, use the switch on Work.
  • Dependencies. An issue can need another issue or a task, and a task can need an issue. Each edge says why, whether it is hard or soft, who declared it and whether you confirmed it. Blocks are worked out from Needs, never typed. An edge Claude proposed waits for you, and the “unblocks” weight counts only confirmed edges.
  • The report. It opens like a task page: kind and state, the title, one sentence (your goal or the symptom), “What I need from you” when something waits, the tabs, and one headline such as “Fix 2 chosen” or “0.6 s”. Every section below is a closed one-line row in a fixed order, marked you, Claude or machine; open only what you want, and the page remembers per kind. Inside a section, code, stacks, attachments and a fix's approach sit behind a second fold. Severity, dependencies, time and origin are closed rows under “About this issue”.
  • “What I need from you”. Every report has one strip at the top for each thing waiting on you: answer, confirm or remove an edge, review assumptions, set a target, choose a fix, confirm a severity. When nothing waits, the strip is not shown.

What is clickable

  • Every chip opens a popover (an anchored card on desktop, a bottom sheet on phone and Rider) with the thing itself, its origin, back-links, Open and Copy link. Open always lands on the right screen.
  • Navigation: list to detail, tab to tab, breadcrumb chips, Back (hash history), the bottom bar on phone, the icon rail in Rider, the left navigation on desktop, the “⋯ More” menu on phone.
  • Review controls: layout switcher, project filter (applies everywhere), inbox sort and deferred toggle, Work filters and Outline/Columns, Files scope, rulings search.
  • Buttons that would change data raise a toast and change nothing, for example “Instruction sent to the Host on laptop for session c21e”. Folds, plan Change mode, settle choices, flips and tick boxes respond on screen.
  • Replies: every card's reply box takes your own text; Send or Enter raises a toast naming the session and machine that would receive it.
  • Issue reports: choose a fix, confirm or remove an edge, set a target, confirm a severity. Each updates the strip and the unblock weight on screen.
  • Overlays: Talk (the chat brief, shown disabled), Add item, Move, Rename, Message, Reassign, Make a ruling, beyond-plan justification.

Counts that must agree

Counts are worked out from the data, not typed into screens: the header meter, the Inbox badge, the Needs you band and Settings all count the same 7 cards; deferred cards are left out. Issue counts on tree rows, the Issues tab and the Issues screen come from the same attach field, and an issue's “needs me” comes from the same list as its strip. An item's “questions n/2” is counted from its open questions, so WB-2.2 shows 2/2 on its cards, its summary and its Questions tab. Comment counts (5 open, 3 handled, 1 stale) are the same in Files, the Comments tab and WB-2's summary. Back-link totals (“cited by”) are worked out by scanning every record for chips.

Limits

  • Fonts fall back to Segoe UI and Consolas because the prototype makes no network calls; the documentation pages load the web fonts.
  • Desktop mode keeps the shell at least 1200 px wide, so a narrower browser scrolls sideways in that mode only.
  • Drag handles in plan Change mode are visual; reordering does not move steps.
  • Layout, theme and fold choices are remembered in this browser only. Choices made on issue reports (fix, edges, target, severity) last until the page is reloaded.
