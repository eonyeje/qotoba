Issue report pattern

Features, bugs and performance problems (FTR, BUG, PER) are issues, not tasks. A task is part of a project's work breakdown; an issue comes up while a task is being built, is attached to that task, and carries its own report and dependencies. This page shows the pattern every report follows, so you can review it apart from the six samples.

Tasks and issues

The tree holds only tasks. Issues hang off the task they were raised on (or off a project with no task yet) and are listed separately on the Issues screen, per task on each task's Issues tab, and as a small count on tree rows. Dependencies can run from an issue to another issue or to a task, and from a task to an issue.

Section order per kind

Each report is a column of titled sections in a fixed order. A section appears only when it has content, so a simple issue is a short page and a complex one is long, but the order never changes. Every section starts as one closed line: its title, who wrote it, and a one-line summary. Open only the ones you want; what you open and close is remembered per kind. A section the templates don't know yet still shows as a closed line with the same shape.

How a report opens

A report shows the least that lets you act, and everything else waits one tap away, the same way a task page does. Nothing below the headline number is open until you open it.

  1. One line of kind: kind, state and severity on the left; the hours it unblocks and Edit on the right. Edit is yours, like Rename on a task: nothing waits on it.
  2. Breadcrumb: project › task › issue.
  3. Title, then one sentence: your goal for a feature, the symptom for a bug. A performance issue has none; its number says it.
  4. Tabs: Report, Plan, Changes, Decisions, Activity.
  5. One headline on the Report tab: “Fix 2 settled”, “2 of 6 steps done”, “0.6 s”, with one quiet line under it, then Taken on by with task chips, or “No task yet”.
  6. Sections as closed one-line rows in the fixed order, each marked you, Claude or machine, starting with When implementing. Nothing on a report asks anything of you; decisions reach you only as inbox cards.
  7. About this item, also closed: Lifecycle (Reported, Taken on, In progress, Done, Verified, moved by task events), Severity (bugs, Claude's proposal), Dependencies (needs, blocks worked out from needs, related, duplicates, what it unblocks), Time, Where it came from (source, the task it hangs off, machine, branch, schedule).
  8. Inside a section, heavy parts wait behind a second fold: pulled code, proposed syntax, a stack, attachments, a fix's approach and files.

When implementing

The first section on every report, written by Claude and kept current. It lists what a task will have to settle before and while implementing the report, and it is the only source a task's decisions are drawn from. It is read only: its lines change because a plan, a Question Card, a run or a packet changed them.

When a task that implements the report is planned, its plan card offers low-cost decisions and dependencies as settle-pass defaults (“Which fix? from BUG-2”), a high-cost decision becomes a Question Card at the step that needs it, and a proof becomes a plan step. Precondition lines that are not met block the plan.

Facts over prose

  • Where a section can show a number, a run, a diff or pulled code, it shows that and not a sentence about it.
  • A claim about behaviour without a run beside it carries a red unverified marker; an acceptance line with no check says no check yet.
  • Code is pulled from files, capped near twelve lines, with Open in Rider and Diff since master. Proposed code sits in a dashed panel marked “not yet written”.
  • Claude's caps: text sections three lines, steps seven, fixes three, the note two lines.
  • Possible fixes are compared in one table: size in Claude-minutes, risk, confidence, whether a regression check exists. Claude marks the one it recommends; the plan of the task that takes the report on settles it.
  • Charts are inline SVG with a caption that states the claim in one sentence.
